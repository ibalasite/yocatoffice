deposit_checkout.feature

# features/deposit/deposit_checkout.feature
# 來源：PRD §4.4 / §5 deposit（US-DEP-001，P1）
# 上游 API：API.md §3 BC: deposit（GET /deposit/packs、POST /deposit/checkout）
# DOC-ID: BDD-SERVER-YOCAT-OFFICE-BACKEND-20261030
# 核心：Phase A 假付費直接確認，經 DepositConfirmed 事件由 wallet BC 入帳；以 Idempotency-Key 冪等。

@deposit @p1
Feature: 儲值訂單建立與目錄查詢
  作為代表玩家的客戶端整合工程師
  我希望查詢可購買的儲值包並以冪等方式建立儲值訂單
  以便讓玩家的儲值動作可信、可對帳且重試不重複入帳

  Background:
    Given 資料庫已初始化為乾淨狀態
    And 儲值目錄已載入，包含寶石包與資本包

  # ─── 正常路徑：公開查詢目錄 ─────────────────────────────
  @p1 @smoke @contract @api @TC-E2E-DEP-001-S01 @US-DEP-001-AC1
  Scenario: 未登入也能查詢儲值包目錄
    Given 使用者未提供 session token
    When 使用者查詢儲值包目錄
    Then 系統回應 HTTP 200 並回傳所有可購買的儲值包
    And 每個儲值包包含包 ID、幣別、入帳數量與顯示名稱

  # ─── 正常路徑：建立訂單（假付費確認）───────────────────
  @p1 @smoke @contract @api @TC-E2E-DEP-002-S01 @US-DEP-001-AC2
  Scenario: 以有效儲值包與冪等鍵建立已確認的儲值訂單
    Given 使用者持有有效的 session token
    And 使用者提供一個全新的冪等鍵
    When 使用者以大寶石包建立儲值訂單
    Then 系統回應 HTTP 200 並回傳狀態為已確認的訂單
    And 回應包含訂單 ID、包 ID、幣別與入帳數量

  # ─── 冪等：重放相同鍵 ───────────────────────────────────
  @p1 @regression @api @TC-INT-DEP-003-S01 @US-DEP-001-AC2
  Scenario: 以相同冪等鍵重放儲值請求時回放原訂單且只入帳一次
    Given 使用者持有有效的 session token
    And 使用者已以某冪等鍵建立過一筆已確認的儲值訂單
    When 使用者以相同的冪等鍵再次送出相同的儲值請求
    Then 系統回放先前那筆訂單的結果
    And 使用者的錢包僅入帳一次

  # ─── 錯誤路徑：冪等鍵衝突（409）────────────────────────
  @p1 @regression @contract @api @TC-INT-DEP-004-E01 @US-DEP-001-AC2
  Scenario: 相同冪等鍵但請求內容不同時回應衝突
    Given 使用者持有有效的 session token
    And 使用者已以某冪等鍵建立過一筆儲值訂單
    When 使用者以相同冪等鍵但不同的儲值包送出請求
    Then 系統回應 HTTP 409 並提示冪等鍵衝突
    And 系統不建立新的訂單

  # ─── 錯誤路徑：儲值包不在目錄（400）───────────────────
  @p1 @regression @contract @api @TC-INT-DEP-005-E01 @US-DEP-001-AC2
  Scenario: 以不存在的儲值包建立訂單時被拒絕
    Given 使用者持有有效的 session token
    And 使用者提供一個全新的冪等鍵
    When 使用者以不在目錄中的儲值包建立訂單
    Then 系統回應 HTTP 400 並提示「儲值包不正確」
    And 系統不建立任何訂單

  # ─── 錯誤路徑：缺冪等鍵（400）──────────────────────────
  @p1 @regression @api @TC-INT-DEP-006-E01 @US-DEP-001-AC2
  Scenario: 未提供冪等鍵時拒絕建立儲值訂單
    Given 使用者持有有效的 session token
    When 使用者在未提供冪等鍵的情況下建立儲值訂單
    Then 系統拒絕請求並要求提供冪等鍵
    And 系統不建立任何訂單

  # ─── 錯誤路徑：未認證（401）─────────────────────────────
  @p1 @regression @contract @api @TC-INT-DEP-007-E01 @US-DEP-001-AC2
  Scenario: 無有效 token 建立儲值訂單時拒絕存取
    Given 使用者未提供有效的 session token
    When 使用者嘗試建立儲值訂單
    Then 系統回應 HTTP 401 並提示「請先登入」
    And 系統不建立任何訂單

domain_event_contracts.feature

# features/cross-module/event/domain_event_contracts.feature
# 來源：EDD §4.6.1 Domain Events / §3.4；API §1.3（Outbox 投遞）
# 跨 BC Domain Event consumer pair：
#   MemberRegistered（member → wallet）、DepositConfirmed（deposit → wallet）、
#   WalletBalanceChanged（wallet → 下游）、EntitlementGranted（entitlement → 下游）、RunScoreSubmitted（leaderboard → 下游）
# DOC-ID: BDD-SERVER-YOCAT-OFFICE-BACKEND-20261030

@event-contract @modulith @p0 @api
Feature: 跨有界上下文領域事件合約
  作為各有界上下文的生產者與消費者
  我希望發布並消費符合合約的領域事件
  以便跨模組狀態保持一致且事件結構升版時不破壞消費端

  Background:
    Given 跨模組通訊一律透過交易式 Outbox 的領域事件進行

  # ─── MemberRegistered 生產者 ───────────────────────────
  @TC-INT-EVT-001-S01 @US-PLAT-001-AC4
  Scenario: 註冊完成時 member 發布合規的會員註冊事件
    Given member 已在同一交易建立新帳號
    When 該交易提交完成
    Then 系統發布會員註冊事件
    And 事件內容包含帳號 ID 與 email
    And 事件結構符合既有合約版本

  # ─── MemberRegistered 消費者（wallet 開帳）─────────────
  @TC-INT-EVT-002-S01 @US-WAL-001-AC1
  Scenario: wallet 消費會員註冊事件後建立初始錢包與開帳帳本
    Given wallet 尚未為該帳號建立錢包
    When wallet 收到合規的會員註冊事件
    Then wallet 為該帳號建立初始餘額為零的錢包
    And wallet 寫入一筆原因為開帳的錢包異動記錄
    And 整個過程不需呼叫 member 的任何 HTTP 介面

  # ─── DepositConfirmed 生產者 ───────────────────────────
  @TC-INT-EVT-003-S01 @US-DEP-001-AC2
  Scenario: 儲值確認後 deposit 發布合規的儲值確認事件
    Given deposit 已建立一筆已確認的儲值訂單
    When 該訂單交易提交完成
    Then 系統發布儲值確認事件
    And 事件內容包含帳號 ID、訂單 ID、幣別與金額

  # ─── DepositConfirmed 消費者（wallet 入帳，冪等）───────
  @TC-INT-EVT-004-S01 @US-WAL-001-AC1
  Scenario: wallet 消費儲值確認事件後入帳且重複投遞只入帳一次
    Given wallet 尚未處理某筆儲值確認事件
    When wallet 收到該儲值確認事件並再次收到相同事件
    Then wallet 僅對該帳號入帳一次
    And wallet 以事件 ID 去重避免重複入帳

  # ─── EntitlementGranted 生產者 ─────────────────────────
  @TC-INT-EVT-005-S01 @US-ENT-001-AC1
  Scenario: 授予權益後 entitlement 發布合規的權益授予事件
    Given entitlement 已在同一交易完成扣款與授予
    When 該交易提交完成
    Then 系統發布權益授予事件
    And 事件內容包含帳號 ID、類別與項目 ID

  # ─── RunScoreSubmitted 生產者 ──────────────────────────
  @TC-INT-EVT-006-S01 @US-LB-001-AC1
  Scenario: 上榜後 leaderboard 發布合規的分數提交事件
    Given leaderboard 已以場次 ID upsert 寫入分數
    When 該寫入完成
    Then 系統發布分數提交事件
    And 事件內容包含帳號 ID、場次 ID、模式與分數

entitlement_purchase.feature

# features/entitlement/entitlement_purchase.feature
# 來源：PRD §5.3 entitlement（US-ENT-001，AC-1～AC-5）
# 上游 API：API.md §3 BC: entitlement（POST /entitlements/buy、GET /entitlements）
# DOC-ID: BDD-SERVER-YOCAT-OFFICE-BACKEND-20261030
# 核心：原子扣款 + 授予同一交易；UNIQUE(account,kind,item) 防重複；破產不消失。

@entitlement @p0
Feature: 已購權益的原子購買與查詢
  作為透過客戶端的辦公室模擬老闆
  我希望以原子交易購買外觀、夢想員工或劇本，且已購權益不重複、不因破產消失
  以便確保花錢買的與特聘的夢想員工永遠不會被搞丟

  Background:
    Given 資料庫已初始化為乾淨狀態
    And 已存在登入中的帳號，其錢包餘額為 cash 18750、gems 330

  # ─── 正常路徑：購買（AC-1）──────────────────────────────
  @p0 @smoke @contract @api @TC-E2E-ENT-001-S01 @US-ENT-001-AC1
  Scenario: 餘額足夠且未擁有時原子扣款並授予權益
    Given 使用者尚未擁有外觀項目 "suit_gold"
    And 使用者的寶石餘額足以支付該項目
    When 使用者以寶石購買外觀項目 "suit_gold"
    Then 系統回應 HTTP 200 並回傳扣款後的錢包與最新權益清單
    And 系統在同一交易寫入一筆購買原因的錢包異動記錄
    And 新權益出現在使用者的權益清單中

  # ─── 正常路徑：免費授予（amount = 0）───────────────────
  @p1 @regression @api @TC-INT-ENT-006-S01 @US-ENT-001-AC1
  Scenario: 以零金額免費授予活動權益時僅插入權益不寫帳本
    Given 使用者尚未擁有劇本項目 "event_welcome"
    When 系統以零金額免費授予該劇本項目
    Then 使用者取得該劇本權益
    And 系統不寫入任何錢包異動記錄

  # ─── 錯誤路徑：已擁有（AC-2）────────────────────────────
  @p0 @regression @contract @api @TC-INT-ENT-002-E01 @US-ENT-001-AC2
  Scenario: 重複購買已擁有的項目時回應衝突且不重複扣款
    Given 使用者已擁有外觀項目 "suit_gold"
    When 使用者再次購買相同的外觀項目 "suit_gold"
    Then 系統回應 HTTP 409 並提示「已經擁有這個項目」
    And 系統不重複扣款也不重複授予

  # ─── 錯誤路徑：餘額不足（AC-3）──────────────────────────
  @p0 @regression @contract @api @TC-INT-ENT-003-E01 @US-ENT-001-AC3
  Scenario: 餘額不足時交易回滾不扣款也不授予
    Given 使用者尚未擁有夢想員工 "soul_einstein"
    And 使用者的餘額小於該項目價格
    When 使用者嘗試購買該夢想員工
    Then 系統回應 HTTP 402 並提示「餘額不足」
    And 使用者未取得該權益且餘額維持不變

  # ─── 邊界條件：項目驗證（AC-4）──────────────────────────
  @p0 @regression @api @TC-UNIT-ENT-004-B01 @US-ENT-001-AC4
  Scenario Outline: 類別非法或缺項目 ID 的購買被拒絕
    Given 使用者持有有效的 session token
    When 使用者以類別 "<kind>" 與項目 "<item_id>" 送出購買
    Then 系統拒絕購買並提示「項目不正確」
    And 系統不授予任何權益

    Examples:
      | kind      | item_id    |
      | weapon    | suit_gold  |
      | cosmetic  |            |
      |           | suit_gold  |

  # ─── 錯誤路徑：未認證（401）─────────────────────────────
  @p0 @regression @contract @api @TC-INT-ENT-007-E01 @US-ENT-001-AC1
  Scenario: 無有效 token 購買權益時拒絕存取
    Given 使用者未提供有效的 session token
    When 使用者嘗試購買外觀項目
    Then 系統回應 HTTP 401 並提示「請先登入」
    And 系統不授予任何權益

  # ─── 正常路徑：查詢權益、破產不消失（AC-5）─────────────
  @p0 @smoke @contract @api @TC-E2E-ENT-005-S01 @US-ENT-001-AC5
  Scenario: 帳號破產重經營後已購權益仍完整列出
    Given 使用者已擁有外觀項目 "suit_gold" 與夢想員工 "soul_einstein"
    And 該帳號曾在遊戲內破產並重經營
    When 使用者查詢已購權益清單
    Then 系統回應 HTTP 200 並完整列出先前購買的所有權益
    And 權益清單依取得時間排序

  # ─── 錯誤路徑：查詢未認證（401）────────────────────────
  @p1 @regression @api @TC-INT-ENT-008-E01 @US-ENT-001-AC5
  Scenario: 無有效 token 查詢權益時拒絕存取
    Given 使用者未提供有效的 session token
    When 使用者嘗試查詢已購權益清單
    Then 系統拒絕存取並提示「請先登入」
    And 系統不回傳任何權益資料

game_save_sync.feature

# features/game-save/game_save_sync.feature
# 來源：PRD §5.4 game-save（US-SAVE-001，AC-1～AC-5）
# 上游 API：API.md §3 BC: game-save（PUT /save、GET /save）
# DOC-ID: BDD-SERVER-YOCAT-OFFICE-BACKEND-20261030
# 核心：以 (account_id, slot) upsert 跨裝置存檔；查無回 {save:null}（非 404）；body 上限 4MB。

@game-save @p0
Feature: 跨裝置辦公室存檔同步
  作為透過客戶端的辦公室模擬老闆
  我希望以帳號上傳辦公室存檔並在任何裝置還原
  以便換手機或重灌後延續公司經營進度，不再因綁單一裝置而全失

  Background:
    Given 資料庫已初始化為乾淨狀態
    And 已存在一個登入中的帳號

  # ─── 正常路徑：上傳存檔（AC-1）──────────────────────────
  @p0 @smoke @contract @api @TC-E2E-SAVE-001-S01 @US-SAVE-001-AC1
  Scenario: 上傳存檔時以帳號與存檔槽 upsert 寫入
    Given 使用者持有有效的 session token
    When 使用者將辦公室存檔上傳至預設存檔槽
    Then 系統回應 HTTP 200 並確認存檔已寫入
    And 該存檔的最後更新時間被更新為當下

  # ─── 邊界條件：缺 data（AC-4）───────────────────────────
  @p0 @regression @contract @api @TC-UNIT-SAVE-004-B01 @US-SAVE-001-AC4
  Scenario: 上傳存檔缺少資料欄位時被拒絕
    Given 使用者持有有效的 session token
    When 使用者在未提供存檔資料的情況下上傳存檔
    Then 系統回應 HTTP 400 並提示「缺 data」
    And 系統不寫入任何存檔

  # ─── 邊界條件：空物件視為合法存檔 ──────────────────────
  @p1 @regression @api @TC-INT-SAVE-006-B01 @US-SAVE-001-AC1
  Scenario: 上傳空物件存檔時仍視為合法寫入
    Given 使用者持有有效的 session token
    When 使用者上傳一個內容為空物件的存檔
    Then 系統確認存檔已寫入
    And 後續查詢可取回該空物件存檔

  # ─── 錯誤路徑：未認證（401）─────────────────────────────
  @p0 @regression @contract @api @TC-INT-SAVE-007-E01 @US-SAVE-001-AC1
  Scenario: 無有效 token 上傳存檔時拒絕存取
    Given 使用者未提供有效的 session token
    When 使用者嘗試上傳存檔
    Then 系統回應 HTTP 401 並提示「請先登入」
    And 系統不寫入任何存檔

  # ─── 正常路徑：還原存檔（AC-2）──────────────────────────
  @p0 @smoke @contract @api @TC-E2E-SAVE-002-S01 @US-SAVE-001-AC2
  Scenario: 查詢已存在的存檔時回傳最新內容
    Given 使用者持有有效的 session token
    And 該帳號的預設存檔槽已有一份存檔
    When 使用者查詢預設存檔槽
    Then 系統回應 HTTP 200 並回傳最新存檔資料與更新時間

  # ─── 邊界條件：無存檔回 null（AC-3）────────────────────
  @p0 @regression @contract @api @TC-INT-SAVE-003-E01 @US-SAVE-001-AC3
  Scenario: 查詢尚無存檔的存檔槽時回傳空存檔而非找不到
    Given 使用者持有有效的 session token
    And 該帳號的預設存檔槽尚無任何存檔
    When 使用者查詢預設存檔槽
    Then 系統回應 HTTP 200 且存檔內容為空
    And 系統不回應資源不存在錯誤

  # ─── 正常路徑：跨裝置還原（AC-5）───────────────────────
  @p0 @smoke @api @TC-E2E-SAVE-005-S01 @US-SAVE-001-AC5
  Scenario: 在一台裝置上傳後於另一台裝置登入可還原同一存檔
    Given 使用者已在裝置 A 上傳了一份辦公室存檔
    When 使用者在裝置 B 以同一帳號登入並查詢存檔
    Then 系統回傳裝置 A 寫入的最新存檔內容
    And 兩台裝置看到的存檔資料一致

leaderboard_ranking.feature

# features/leaderboard/leaderboard_ranking.feature
# 來源：PRD §5 leaderboard（US-LB-001，P1）；RTM TC-INT-LB-001
# 上游 API：API.md §3 BC: leaderboard（GET /leaderboard、POST /leaderboard）
# DOC-ID: BDD-SERVER-YOCAT-OFFICE-BACKEND-20261030
# 核心：公開 Top N 查詢（不需登入）；上榜歸戶寫入，以 run_id upsert 冪等。

@leaderboard @p1
Feature: 全域排行榜查詢與上榜
  作為代表玩家的客戶端整合工程師
  我希望公開查詢全域排行榜並以歸戶方式上榜且重複提交只更新一筆
